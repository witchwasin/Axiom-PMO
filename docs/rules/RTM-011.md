# RTM-011 - Anti-forged verified status in RTM

| | |
|---|---|
| Level | FAIL |
| Gate | Release |
| Applies to | Strict |
| Artifacts | `RTM.json`, `RELEASE.md` |

## What this rule checks

In `RTM.json`:
When any traceability row claims `status: verified`, all three legs must be satisfied:
1. `delivery_ref` work item in `DELIVERY.md` must have `Status: Done`.
2. `test_ref` test in `RELEASE.md` `## Test Summary` must have `Result: passed`.
3. `PROJECT.md` `## Approvals` must have `Release Approved` row with `Approval Status: approved`.

## Why it blocks

Claiming `status: verified` before code has been delivered, tested, and release-approved is an anti-pattern. An RTM row remains `supported` throughout discovery, design, and handoff, and only transitions to `verified` once work is Done, tests Pass, and Release is Approved.

## How to fix

Keep the row's `status` as `supported` in `RTM.json` until delivery work item is `Done`, test execution in `RELEASE.md` `## Test Summary` is `passed`, and `Release Approved` is recorded.
