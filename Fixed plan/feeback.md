### Human Owner decisions on the four design questions (all resolved)

1. **Contract scope: anchor on `EXECUTION-REVIEW.json` (adversarial), not
   both families.** MasterPlan's L3 description ("does the implementation
   semantically match the requirement and its tests") describes a review of
   *implemented* code — that is what `EXECUTION-REVIEW.json` findings are.
   `HANDOFF-REVIEW.json` findings review completeness *before* code exists,
   so `implementation_claim`/`test_claim` do not fit them naturally, and
   `owner` is already present there — nothing to add. Do not force the
   five-field contract onto handoff findings.
2. **`requirement_ref` resolves against PROJECT.md In Scope (`REQ-###`)
   only.** Reuse `Get-IdsFromRows` the same way RTM does. Do not also resolve
   against `DELIVERY.md` — `item_id` already covers the work-item link;
   duplicating that in `requirement_ref` blurs two different kinds of
   reference into one field.
3. **`implementation_claim`/`test_claim` are conditional, with an explicit
   N/A value when a finding has no natural claim to make** (e.g. a
   build-order or acceptance-seed-reachability finding). Not mandatory
   everywhere — that would force fabricated content into findings that
   genuinely have none. The N/A value must be an explicit, checkable marker
   (not merely absent/blank), so a validator can still tell "not applicable"
   apart from "forgot to fill in."
4. **New sibling rule id, not an extension of `AREV-004`.** Same reasoning as
   `TEST-EVIDENCE-002`/`003`: `AREV-004`'s existing description stays
   truthful and narrow, the new contract gets its own rule id, catalog entry,
   and doc page. Tests for the new fields belong in a **helper suite** (the
   `release-evidence-tests.ps1`/`scope-diff-tests.ps1` disposable-fixture
   style), not the fixture/golden suite — this is JSON review-file field
