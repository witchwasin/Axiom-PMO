# Axiom-PMO 1.4.0 — Release Notes

Onboarding and the two execution paths become part of the core product.
Adversarial review evidence and a local, opt-in failure-pattern registry
ship as two new optional governance capabilities. Includes post-closure
hardening found by real CI after the milestones were merged.

Backward compatible. Every existing project, fixture, and invocation is
unaffected unless it opts into the new capabilities.

## Onboarding and the two execution paths (Milestone 7)

*Core product. Boundary extended from Milestones 1–5 to 1–7 (`DEC-017`).*

`axiom init` now asks two independent questions once, instead of leaving them
to be inferred from the README:

```text
Axis 1 — who builds it?               Development Handoff | Governed AI Execution
Axis 2 — how strictly is it governed?  Lite | Standard | Strict
```

The answer is recorded as a governed `execution_path` declaration
(`development_handoff` or `governed_ai_execution`) in `PROJECT.md`, checked
by `PATH-001` (missing/invalid declaration) and `PATH-002` (a declaration
gone stale against an active `.execution/**` package). A new `axiom status`
verb reports what a project needs next, derived only from the validator's
own diagnostics — never independently composed. Interactive prompting fires
on a TTY only, so CI and `make demo` cannot hang on it.

See [`docs/concepts/execution-paths.md`](../concepts/execution-paths.md),
[`PATH-001`](../rules/PATH-001.md), and [`PATH-002`](../rules/PATH-002.md).

Independently reviewed by Independent AI Reviewer (round 3, final verdict ACCEPT, no finding
raised against this milestone across any round). Human Owner closed and
merged 2026-08-03 (`DEC-016`); boundary extended 2026-08-04 (`DEC-017`)
because onboarding is required infrastructure for using the product at all,
unlike Milestone 6.

## Adversarial review evidence (Milestones 8.0/8.1)

*Optional, adjacent to the core product (`DEC-017`). A project can use
Axiom-PMO fully without ever touching this.*

Adds a third evidence tier alongside `artifact-observed` and
`externally-observed`: a named, independent reviewer's findings, recorded in
`EXECUTION-REVIEW.json` and checked by `AREV-001`..`AREV-006`. An
`externally-observed` (CI-produced) review only counts when it is bound to
the pinned review workflow by commit, status, conclusion, artifact digest,
and workflow-file digest — a `check_run_id` alone proves a CI job ran, not
that the pinned workflow produced it. `closure_policy.settable_by` restricts
certain finding statuses to a human reviewer, enforced per finding, not just
loaded from policy. `axiom verify --preflight` runs the check without
gating a release.

Independently reviewed by Independent AI Reviewer across three rounds (round 1: 1 FATAL + 2
MAJOR, both fixed and regression-tested against a stubbed `gh` CLI since the
live GitHub API cannot be made hermetic for a test suite; round 2: 1
compatibility finding, fixed; round 3: ACCEPT). Two items were recorded as
known limitations rather than implemented, per Independent AI Reviewer's explicit scope lock —
see `docs/architecture/adversarial-review.md` §11.

## Failure pattern registry (Milestone 9)

*Optional, adjacent to the core product (`DEC-017`).*

`scripts/aggregate-diagnostics.ps1` aggregates existing validator
diagnostics into one immutable, per-run event file and a rebuildable
`FAILURE-PATTERNS.json`. Local and opt-in: no network transmission, raw
events git-ignored by default. Every retained field carries an explicit
retain/normalize/hash/drop disposition — "metadata-only" is not by itself a
privacy guarantee. A cluster crossing a configured threshold produces an
`IMPROVEMENT-CANDIDATE.json`; an AI-authored one may only ever carry
`status: proposed`. `DOCTOR-014` enforces that an `experimental` rule can
never be blocking severity.

Independently reviewed by Independent AI Reviewer (round 1: 1 MAJOR, fixed; round 3: ACCEPT).

## Post-closure hardening

Three defects were found by real GitHub Actions CI **after** the four
milestones above were closed and merged — none of them visible to any check
that existed at review time, and each fixed and re-verified against real CI,
not self-reported evidence. Full detail in `CHANGELOG.md`.

- **`Out-String` newline reconstruction** (Milestone 8.1). Recomputing a
  pinned workflow's digest through `git show | Out-String` rejoined stripped
  lines with the *platform* newline — correct by coincidence on Linux/macOS,
  always wrong on Windows, so the `externally-observed` tier could never
  verify there. Fixed by reading the git blob's exact bytes via
  `git cat-file blob` and `Start-Process -RedirectStandardOutput`.
- **`RandomNumberGenerator::Fill()` absent on Windows PowerShell 5.1**
  (Milestone 9). A .NET Core 2.1+ API; 5.1 runs on .NET Framework, so the
  aggregator threw before writing any event on that host. Fixed with
  `RNGCryptoServiceProvider`. This also surfaced a **vacuously-passing**
  privacy test — three "no event carries field X" assertions reported PASS
  against an empty string when zero events were written. Now anchored on
  the event text being non-empty; a full audit of `tests/helpers/*.ps1`
  found and fixed one further instance of the same pattern.
- **CI timeout budget** (workflow infrastructure, not milestone code). The
  Windows PowerShell 5.1 job was killed twice by a 15-minute timeout that no
  longer fit the suite the milestones above grew; every check that ran
  before the cutoff was PASS. Raised to 30 minutes on both Windows jobs.

Independently acknowledged by Independent AI Reviewer: `DEC-016` stands, none of the four
milestones reopen, and the CI-timeout fix is a workflow-infrastructure
change, not a milestone code change.

## Product boundary change (`DEC-017`)

`ROADMAP.md`'s Milestone 7 entry had stated "Core product" without a
corresponding Human Owner decision — `DEC-006` covered only Milestones 1–5
and 6. `DEC-017` (2026-08-04) resolves this: the core-product boundary is
extended to Milestones 1–7. Milestones 8.0, 8.1, and 9 remain optional,
adjacent governance capabilities, on the same footing as Milestone 6.

## Upgrading from 1.3

No migration required.

- `execution_path` defaults to `development_handoff` for every existing
  project and fixture, so nothing changes until a project explicitly
  declares `governed_ai_execution`.
- Adversarial review evidence and the failure-pattern registry are both
  opt-in: a project that never creates `EXECUTION-REVIEW.json` or runs
  `aggregate-diagnostics.ps1` sees no behavior change.
- If you run `pmo-checks` in a fork or a self-hosted runner and previously
  matched CI duration against the old 15-minute Windows timeout, expect the
  Windows jobs to now run up to 30 minutes under load; this is a raised
  ceiling, not a slower suite.
