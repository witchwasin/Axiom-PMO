# Axiom-PMO 1.1.0 — Release Notes

**Handoff-Ready.** A checking layer between `Design` and `Release` that answers a
question 1.0 could not.

```text
Draft → Scope → Design → Handoff → Build/QA → Release
```

## The gap this closes

1.0 could prove that governance was complete: every requirement sourced, every
gate approved, every claim backed by resolvable evidence. It could not answer the
question a delivery lead actually asks before handing work over:

> Is this enough for someone to start on Monday, and will it demo on time?

A project can satisfy every 1.0 check and still hand a developer a plan that
cannot be executed:

- the shared schema every other item reads from is scheduled *after* the items
  that consume it — two engineers spend day one building against nothing;
- a scan feature needs the device camera and nobody decided how the page is
  served, so it works on `localhost` and does nothing on the demo tablet, and no
  code review catches it because nothing in the code is wrong;
- one document commits to keeping photographs on the site network while another
  specifies a photo upload with no classification — both authors were accurate
  about their own page;
- an acceptance case asserts behaviour on a record type the seed data never
  creates, so it is never actually run;
- a work item is owned by "Dev Team", which survives every status meeting and
  dies on Monday morning.

Each is invisible to a rule that checks whether a field is filled in. Each costs
days.

## Two layers, deliberately separate

The temptation is to encode those failures as validator rules: *stock features
need a receive operation*, *photos are PII*, *QR scanning requires HTTPS*. Each
is true in some domains and wrong in others, and a validator that guesses wrong
teaches people to ignore it.

| Layer | Owns | Mechanism |
|---|---|---|
| Deterministic validation | What is provable from the artifacts | `-Gate Handoff`, rules `HANDOFF-001`–`HANDOFF-012` |
| Semantic handoff review | Whether the complete contract makes sense | `pmo-delivery` intent `handoff_review`, recorded in `HANDOFF-REVIEW.json` |

The deterministic layer reads declarations the author wrote and checks they are
complete, resolvable, and owned. `HANDOFF-011` fires when a row marked "Contains
Sensitive Data = yes" has no classification decision — never because the row is
called "photo".

The semantic layer supplies judgement. The deterministic layer's only interest in
it is mechanical: did a review happen, did it cover every lens, does every
finding have an owner and a blocking point, and is it still current.

**A semantic review is candidate evidence, not an approval.**

## Readiness is not one boolean

`scripts/assess-handoff.ps1` reports six stage verdicts:

```text
Verdict: READY TO BUILD, NOT READY TO DEMO

  YES  Contract Valid                no deterministic failures
  YES  Ready to Start Development    no recorded blocker
  YES  Ready to Integrate            no recorded blocker
  NO   Ready to Demo                 blocked by HF-005, OA-001
  NO   Ready for UAT                 blocked by HF-005, OA-001
  NO   Ready for Release             blocked by HF-005, OA-001
```

Collapsing that into one answer forces a bad choice. "Not ready" stalls a team
that could be working. "Ready" promises a demonstration that will not happen.

Each verdict is `true`, `false`, or **`null`** for "cannot be determined" —
usually because no usable review exists. An absence of recorded findings is
never reported as an absence of problems. Blockers are drawn from both
`HANDOFF-REVIEW.json` findings and `HANDOFF.md` open actions, deduplicated.

The accompanying 100-point score is capped hard whenever the evidence behind it
is thin — `BLOCKED` on any deterministic FAIL, max 70 without a usable review,
max 69 with a missing owner or an unexecutable build sequence, max 49 with an
open critical `before_build` finding. Open findings and open actions each cost
points in the dimension they belong to, so a project cannot score full marks
while its own documents say the demonstration will fail. **It is not an
approval.**

## What is new

| | |
|---|---|
| Gate | `Handoff`, reusing the existing `Design Ready` approval — no new sign-off |
| Rules | `HANDOFF-001`–`HANDOFF-014`, each with a `docs/rules/` page |
| Artifacts | `HANDOFF.md`, `DESIGN/BUILD-SPEC.md`, `HANDOFF-REVIEW.json` |
| Diagnostics | v1.1 adds `artifact`, `item_id`, `field`, `suggestion`, `documentation_url`, `schema_version` |
| Scripts | `assess-handoff.ps1`, `handoff-digest.ps1`, `demo.ps1` |
| CLI | `cli/axiom.mjs` — `demo`, `check`, `doctor`, `validate`, `handoff`, `init` |
| Demo | `demo/broken-project` and `demo/fixed-project`, runs in seconds |
| Doctor | `DOCTOR-008` (every fail/warn rule has a suggestion), `DOCTOR-009` (every doc path resolves) |
| Freshness | Two digests — `source_snapshot` and `review_inputs` — so editing a reviewed artifact invalidates the review, not just changing the sources |
| Closure authority | Enforced, not requested: every non-`open` status needs a resolvable `decision_ref`, an AI may only set `resolved`, and a human-only lens needs a `DEC-###` with a named decider |
| Readiness | Six stage verdicts, tri-state (`true` / `false` / `null`) with a reason each; blockers merged from review findings **and** `HANDOFF.md` open actions |

## Fixed

Defects that predate this release:

- **The test suite could not run on PowerShell 7.** Child invocations were
  hardcoded to `powershell`, so the whole fixture matrix reported `PASS=0
  FAIL=95` on any non-5.1 host — for reasons unrelated to the validator.
- **A count rendered as empty in a diagnostic.** `Where-Object` results used
  without `@()` return a bare object when exactly one row matches, so the message
  read `" requirement line(s) may be missing source_ref"`. Two golden masters had
  recorded the defective text as expected.
- **Generated dates used the wrong calendar.** Under a Thai locale every
  generated project was dated in the Buddhist year (`2569-07-26`).
- **Golden masters were host-specific.** BOM, JSON indentation, numeric escapes,
  and path separators differ between PowerShell hosts, so `-VerifyGolden` failed
  wholesale whenever the verifying host differed from the capturing one.
- **The release helper suggested `v1.0.0`.** It now derives the tag from
  `VERSION`.

And defects introduced while building 1.1, found in review before release:

- `axiom handoff --json` emitted two documents with labels between them; the
  CLI also truncated piped JSON at 8 KB via `process.exit()`.
- A `Contains Sensitive Data` cell reading `maybe` skipped `HANDOFF-011`
  entirely, because anything that was not a recognised "yes" was treated as a
  "no".
- An open action blocked a stage verdict without costing score, printing a
  perfect number directly above `Ready to Demo: NO`.
- Human-only closure rested on a self-declared `reviewer_kind`.
- An explicitly empty `AllowedSecondaryRules` silently disabled the fixture
  isolation check it was written to express.
- A template placeholder regex used `(?m)$` against raw file text, which cannot
  match on the CRLF line endings a Windows checkout produces. The generated
  project kept its placeholders and failed its own Handoff gate -- green on the
  Linux CI leg, red on Windows.
- Freshness digests and diagnostic ordering used culture-sensitive sorting, so
  a review recorded on one machine could read as stale on another.
- A stale review still printed a PASS saying it was current.
- The missing-PowerShell CLI test emptied `PATH`, which hides the host on POSIX
  but not on Windows.

## Compatibility

**No migration required.** Projects that do not request the new gate validate
exactly as they did in 1.0.

- The v1.0 diagnostic fields `level`, `rule_id`, `message`, `blocking` keep their
  names, meanings, and relative order. A v1.0 consumer reads v1.1 output
  unchanged.
- New fields are always present, `null` when they do not apply — never omitted,
  never `""`.
- Exit codes unchanged: `0` pass, `1` fail, `2` blocking warning under
  `-FailOnWarning`. The CLI adds `127` (no PowerShell host) and `64` (usage),
  neither of which the validator emits.
- Handoff artifacts are reported only when the artifact matrix asks for them, so
  runs at other gates produce no new rows.
- `new-project.ps1` default output is unchanged; handoff scaffolding is opt-in
  via `-IncludeHandoff`.

Full detail in the [changelog](../../CHANGELOG.md).

## Adopting the gate

```bash
node cli/axiom.mjs demo                                    # see what it catches
node cli/axiom.mjs init --code P02-ABC --handoff --target demo
node cli/axiom.mjs handoff --project projects/P02-ABC --mode Standard
```

worked walkthrough in

## Known limitations

Stated so nobody has to discover them.

**Attribution is traceable, not provable.** `reviewer_kind` is a self-declaration; no offline validator can prove who typed a JSON field. A closure under a human-only lens must cite a `DEC-###` that exists in `decision-log.md` with a named decider, which anchors it to a governed artifact somebody is accountable for. Provable attribution needs signed commits or a reviewed pull request — both outside this validator.

**Cross-platform support is evidence, not a claim.** Windows PowerShell 5.1 remains the reference platform. PowerShell 7 on Linux/macOS is exercised by a **non-blocking** CI leg. Promote it only once it has a track record.

**No clean-room walkthrough or terminal recording.** ([#8](https://github.com/witchwasin/Axiom-PMO/issues/8)) Milestone 1 asks for both. `scripts/demo.ps1 -Plain -NoPause` produces a deterministic transcript to record, and `demo/README.md` gives the `asciinema` command, but no asset is committed and no independent first-run walkthrough has been performed. Nothing here claims otherwise.

> *Since 1.1.0:* `clean-room/` now ships a container for the walkthrough, and
> #8 is closed as **not planned** — tracked but deferred, not done. See the
> [1.1.1 notes](v1.1.1.md#known-limitations).

**Location fields are partially populated.** `artifact` / `item_id` / `field` are filled by every `HANDOFF-*` rule and progressively by the older ones. `null` is a valid state, documented in the [diagnostics contract](../reference/diagnostics-contract.md).

**Rule pages cover the handoff rules only.** Other rules carry their remediation in the catalog entry.
