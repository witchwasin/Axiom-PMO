# API-002 - OpenAPI operationId correspondence with BUILD-SPEC

| | |
|---|---|
| Level | FAIL |
| Gate | Handoff, Release |
| Applies to | Standard, Strict (when `Spec depth: full` and OpenAPI spec is present) |
| Artifacts | `DESIGN/API/openapi.yaml`, `DESIGN/BUILD-SPEC.md` |

## What this rule checks

When `DESIGN/API/openapi.yaml` exists and `DESIGN/BUILD-SPEC.md` defines an `API or Command Contract` table:
The validator uses a lightweight zero-dependency YAML scanner to extract all declared `operationId:` occurrences in `openapi.yaml`. Every `Operation ID` declared in `BUILD-SPEC.md` must correspond to a declared `operationId:` in `openapi.yaml`.

## What the validator deliberately does not decide

This rule verifies **operationId presence and correspondence**, not complete JSON/OpenAPI schema validation or payload semantics. Full schema validation is delegated to dedicated schema tooling during CI/CD execution.

## Why it blocks

When operation IDs in the architectural spec diverge from the API contract file, frontend/backend teams build against mismatched endpoint interfaces.

## How to fix

Ensure every `Operation ID` in the `BUILD-SPEC.md` API Contract table is defined as an `operationId:` in `DESIGN/API/openapi.yaml`:

```yaml
paths:
  /api/v1/resource:
    get:
      operationId: getResource
```
