# Axiom-PMO 2.0.0 — Release Notes

MasterPlan v.2.0 asked one question before writing any code: should
[AxiomGuard](https://github.com/witchwasin/AxiomGuard) — a separate,
read-only Z3 formal-verification engine — become a fourth verification level
that proves Axiom-PMO's own governed artifacts internally consistent? An M0
spike tested that question against the pinned engine before committing to a
build. The answer was no, with evidence, and 2.0 ships the two things the
spike's own findings justified instead: a semantic output contract on
AI-executed adversarial review findings, and repository ground-truth
reconciliation for test evidence on both the execution and release paths.

Backward compatible. Every existing project, fixture, and invocation is
unaffected unless it opts into the new capabilities.

## Declined: L4 formal verification (`DEC-024`)

*AxiomGuard was read only throughout — this repository never modifies it.*

The spike hand-encoded `pmo-config/policy.json` and `artifact-policy.json` as
25 rules / 56 Z3 constraints against the pinned `axiomguard==0.7.2`, and ran
four experiments:

- **A** — the current config's legitimate Lite/Standard/Strict releases are
  consistent (3/3 SAT).
- **B** — deliberately contradictory scenarios are all caught (7/7 UNSAT) —
  but every one maps to a rule the existing 114-rule catalog already
  enforces.
- **C** — the engine is structurally blind to role-string membership: no rule
  type expresses "this value must be one of a closed set," so an orphan
  `"Project Owner"` role (fixed separately below) went undetected.
- **D** — enumerating 160 release scenarios found zero reachability holes the
  existing rules miss.

Nothing justified adding a Python/Z3 dependency to the maintainer toolchain
for it. L4 (the compiler, the adapter, `DOCTOR-0xx`) is declined — recorded
as `DEC-024`, reversible, the same posture as the npm/marketplace declines.
The spike itself lives at `Fixed plan/m0-spike/` for anyone who wants to
re-run it.

## Added: semantic output contract on adversarial review findings (`AREV-007`)

*Closes `DEC-025`. Anchored on `EXECUTION-REVIEW.json` only — the handoff
review family is untouched.*

Every finding an AI records in an adversarial review of executed code must
now carry:

- **`requirement_ref`** — the `REQ-###` it speaks about, resolving against
  `PROJECT.md`'s In Scope table.
- **`implementation_claim`** / **`test_claim`** — one sentence each, or the
  explicit `"N/A"` marker when the finding has no natural claim to make. A
  blank field is a violation; "not applicable" must be stated, never implied.
- **`owner`** — a named human accountable for the finding, never a group
  token ("Dev Team", "TBD") — checked with the same `owner_policy` the
  handoff family already uses.

This is a shape check only. It never judges whether a review's content is
thorough or correct, and it never reads a review's `recommendation` field —
an AI's semantic verdict still cannot change a validator's exit code on its
own, the same rule `HANDOFF-010` already enforces. See
[`docs/rules/AREV-007.md`](../rules/AREV-007.md).

## Added: repository ground truth for test evidence (`EXEC-005`, `TEST-EVIDENCE-003`)

*Closes the remaining "claimed vs. actual" gap M4 targeted: an agent report
claiming tests pass must not survive a gate when git itself contradicts it.*

**Execution path.** A required test backed only by artifact-tier evidence,
with no human vouch, now gets a sharper reason when its `junit-artifact` was
never part of the verified `base..head` range: *"a report that predates the
work cannot prove the changed code passes"* — instead of only the generic
provenance complaint. The existing human-vouch escape hatch is unchanged.

**Release path (new, opt-in).** `validate-project.ps1` gains
`-ReleaseDiffBase` / `-ReleaseDiffHead`, mirroring `-ScopeDiffBase` /
`-ScopeDiffHead` exactly: omitted by every existing caller, so behavior is
byte-identical for them. When supplied, a passed Test Summary row's `FILE:`
evidence is checked against the verified commit range: stale evidence is
WARN-blocking at Standard and FAIL at Strict — the same two-tier severity
`APPROVAL-003` already uses. Untracked/gitignored evidence stays out of
scope by design (invisible to `git diff` regardless of freshness, so flagging
it would be a false positive), and there is no human-vouch escape hatch on
this path — it is the last checkpoint before release. See
[`docs/rules/EXEC-005.md`](../rules/EXEC-005.md) and
[`docs/rules/TEST-EVIDENCE-003.md`](../rules/TEST-EVIDENCE-003.md).

## Added: `Design Ready` approvable by `Product Owner` or `Project Manager` (`DEC-023`)

A small team without a `Tech Lead` or `Solution Architect` title could not
clear `Design Ready` even when a `Product Owner` or `Project Manager` had
reviewed it — the role matrix blocked a real human approval on a title
technicality, not a missing review. `pmo-config/policy.json`'s `Design Ready`
approval roles now accept `Product Owner` and `Project Manager` alongside the
existing two. Nothing else changes: `Scope Approved`, `Release Approved`, QA,
security, and privacy authority are all unchanged, and an AI still cannot
approve its own work.

## Fixed: `RELEASE-001`'s suggestion text was stale after the waiver fix

The M0 spike also surfaced two config defects unrelated to the L4 decision
itself: an orphan `"Project Owner"` role string (a typo for `"Project
Manager"`, now closed by a new `enums.roles` list), and an unexplained
asymmetry between `test_waiver` and `rollback_waiver`'s allowed modes (both
now allow Lite and Standard). `RELEASE-001`'s suggestion text and
`templates/RELEASE.md` still said the rollback waiver was Lite-only after
that fix; corrected, with 14 golden files updated to match (each a
single wording-only line).

## Fixed: `main` was failing `pmo-doctor` after the CHANGELOG entry landed

`DOCTOR-005` requires `VERSION`, `CHANGELOG.md`'s top heading, and the
`version` field in six `pmo-config/*.json` files to agree. Adding this
release's `## 2.0.0` CHANGELOG heading without bumping those was an
oversight that stayed invisible through review — the entry had been staged
directly into the git object database (to avoid colliding with another
session's unrelated, uncommitted `CHANGELOG.md` edit), so the working-tree
file was never actually written to disk, and `DOCTOR-005` was never exercised
against the real content until a later verification pass caught it live on
`main`. Fixed by bumping `VERSION` and all six checked config files to
`2.0.0`, matching the CHANGELOG heading this release note itself sits under.
