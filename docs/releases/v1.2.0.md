# Axiom-PMO 1.2.0 — Release Notes

A feature release: Axiom-PMO ships as a reusable GitHub Action, and gains a
deterministic check that a pull request's changed files stayed inside a
project's pre-approved implementation scope.

Backward compatible. No existing local invocation — `validate-project.ps1`,
`assess-handoff.ps1`, the CLI — changes behaviour or output. The Action and
SCOPE-DIFF are both opt-in.

## GitHub Action

*Milestone 4.*

```yaml
- uses: witchwasin/Axiom-PMO@v1.2.0
  with:
    project: projects/P02-MYPROJECT
    mode: Standard
    gate: Release
```

Ten lines or fewer to add to a workflow. The Action is a thin wrapper around
the same PowerShell validator every local invocation already uses — it
contains no duplicated validation logic, so a governance rule behaves
identically whether it runs on a developer's machine or inside CI.

What it produces on every run:

- a GitHub Job Summary, short and fix-oriented;
- `axiom-report.json` and `axiom-report.md`, uploaded even when validation
  fails, so a failed run still leaves evidence behind;
- PR annotations mapped to `artifact`, `item_id`, `field`, and `rule_id`,
  capped and escaped so a workflow-command control character or an
  overlong field can't corrupt the annotation stream.

`enforce` defaults to `false` — a governance failure is fully reported
(Job Summary, annotations, both report files) without failing the workflow
step, so a team can see what the Action would block before turning
enforcement on. `SCOPE-DIFF-003`/`004` (an invalid declaration or an
unresolvable git range) are treated as infrastructure failures, not
governance verdicts, and are never hidden by report-only mode — the same
principle as a missing PowerShell host always failing the step.

Privacy carries the same standard as every local diagnostic: a failed
command's raw stdout/stderr never reaches a report, annotation, or Job
Summary. Only a small set of known, safe messages do; the underlying detail
goes to the workflow run log, which is not an uploaded artifact.

See [`docs/guides/github-action.md`](../guides/github-action.md) for the full
input/output reference.

## SCOPE-DIFF — changed-file scope enforcement

*Milestone 4.5.*

Answers one question, deterministically: **did this change stay inside the
file paths that were approved for it?**

A project declares its approved scope once, in `SCOPE.json`:

```json
{
  "schema_version": "1.0",
  "project": "P02-MYPROJECT",
  "implementation_scope": {
    "include": ["src/payments/**", "tests/payments/**"],
    "exclude": ["src/payments/generated/**"]
  }
}
```

Opt in with `enable-scope-diff: true` on the Action, or
`-ScopeDiffBase`/`-ScopeDiffHead` on `validate-project.ps1` directly. Every
existing invocation that supplies neither is unaffected — SCOPE-DIFF is
additive to the validator and the Action.

Design points worth knowing before adopting it:

- **A missing `SCOPE.json` fails closed** (`SCOPE-DIFF-002`). SCOPE-DIFF
  never treats "no declaration" as "everything is approved."
- **A small, deterministic glob grammar** — `*`, `?`, `**`, and literal
  characters only. No character classes, no brace expansion, nothing an LLM
  has to interpret; the same principle as the rest of this validator.
- **Path matching is case-sensitive.** `SRC/PAYMENTS/x.ts` does not satisfy
  `include: ["src/payments/**"]` — a case-insensitive comparison would let a
  path differing only in case slip past scope on a case-sensitive checkout.
- **Renames are checked at both the old and new path**, combined into the
  worse of the two verdicts. The structured `scope_diff.renames[]` field
  carries both paths and both individual verdicts, so external tooling does
  not have to parse a `(renamed from ...)` note out of diagnostic prose.
- **Rename detection does not depend on the runner's own git configuration**
  — `diff.renames` and `diff.renameLimit` are pinned explicitly on every
  invocation, so the same change is reported identically across machines
  and CI images.
- **A small, reviewable repo-wide exemption list**
  (`pmo-config/scope-diff-policy.json`) covers paths reasonable to touch
  alongside any change in any project — lockfiles, `CHANGELOG.md` — without
  repeating them in every project's own `SCOPE.json`. Every entry is
  validated: an empty pattern or reason, a duplicate pattern, or a pattern
  broad enough to match effectively everything (`**`, `*`, `**/*`) is
  rejected outright, because a repo-wide exemption that broad would silently
  disable the check for every project at once.
- **Report-only vs. enforce** follows the same rule as the rest of the
  Action: a scope violation (`SCOPE-DIFF-001`/`005`) is fully reported
  without failing the step unless `enforce: true`; `SCOPE-DIFF-003`/`004`
  (infrastructure failures) are never hidden by report-only mode.

See [`docs/reference/scope-declaration.md`](../reference/scope-declaration.md)
for the full contract, including known limitations (one scope per project
not per work item, rename similarity threshold, no per-repo exemption
override for external consumers).

## Diagnostics contract

New optional `scope_diff` envelope field on `validate-project.ps1 -Format
Json`, present only when SCOPE-DIFF was requested — omitted entirely, not
`null`, on every other run, so an existing consumer's parsing is unaffected.
`diagnostics_schema_version` stays at `1.1`; this is an additive top-level
sibling of `results`, not a change to the per-row diagnostic shape. See
[`docs/reference/diagnostics-contract.md`](../reference/diagnostics-contract.md).

## Compatibility

No migration. `VERSION` and every `pmo-config/*.json` version move to
`1.2.0`; `schema_version` and `diagnostics_schema_version` are unchanged.

A project that does not add `SCOPE.json` or a workflow using the Action sees
no behavioural change at all. A consumer already parsing `axiom-report.json`
keeps working unchanged; `scope_diff` and `action` are new, optional,
namespaced additions.

## Known limitations

Carried forward from [1.1.1](v1.1.1.md), plus SCOPE-DIFF-specific ones:

- **One scope declaration per project, not per work item.** Several work
  items in flight with genuinely different approved scopes currently share
  one combined `SCOPE.json`.
- **Rename detection depends on git's own similarity threshold** (roughly
  50% by default). A heavily-rewritten file that git reports as a plain
  delete + add, rather than a rename, is evaluated as two independent
  changes.
- **Copies are not specially detected.** A copied-then-kept file is
  evaluated the same as a new file: only its own path matters.
- **`pmo-config/scope-diff-policy.json` is shared framework config, not a
  per-repo override for external consumers.** A consuming repository cannot
  currently add its own repo-wide exemptions without a project-level
  `SCOPE.json` `include` entry for each path.
- **No release newer than this one has external-user validation yet.**
  1.1.1 predated the Action and SCOPE-DIFF entirely — this is the first tag
  either feature is available in.
