# REF-002 - FILE: reference escapes the project root

| | |
|---|---|
| Level | FAIL |
| Gate | Draft, Scope, Design, Handoff, Release |
| Applies to | Lite, Standard, Strict |
| Artifacts | any governed reference (`PROJECT.md`, `DESIGN/`, `RTM.json`, approval/test/release evidence) |

## What this rule checks

A `FILE:` reference must resolve to a path **inside** the project root. The reference resolver rejects:

- absolute paths (`/etc/...`, `C:\...`);
- relative paths that canonicalize above the root (`FILE:../../`, `FILE:../..`).

The check runs before the existence check, because the two failures mean different things: a `FILE:` that points at nothing is `evidence_not_found`; a `FILE:` that points at a real file *outside* the project is a containment breach.

## Why it blocks

A `FILE:` reference is the validator's promise that evidence lives where the project lives. A path like `FILE:../../secrets.env` resolves to a real file and would otherwise read as *resolved* - handing an approval or a release claim the weight of evidence the project does not own and should not reach.

## What the validator does not do

It does not fetch remote paths, follow symlinks across the boundary beyond what path canonicalization reveals, or inspect the target file's contents. It checks declared containment only.

## How to fix

Move the referenced file inside the project root, or point the reference at a path that is already inside it.

```text
FILE:../../shared/decision.md      -> FAIL (escapes the project)
FILE:docs/decision.md              -> OK   (inside the project root)
```
