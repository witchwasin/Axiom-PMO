# Axiom-PMO 1.5.0 — Release Notes

Milestone 10 adds **conditional Visual Proof** at the existing Handoff gate,
alongside the optional visual-direction and design-system capabilities it
builds on. Two defects found on `main` are fixed: one CI-infrastructure, one
portability defect that could block a real team's Handoff gate.

Backward compatible. Every existing project, fixture, and invocation is
unaffected unless it opts into the new capabilities.

## Visual direction and design systems (optional)

*Optional creative capability. Not required to reach any gate.*

`pmo-design` gains two intents beyond the default `flow`:

- **`visual_direction`** — turns a source-backed creative brief into explored
  directions and a human-selected one (`DEC-018`, authorized by `DEC-019`).
- **`design_system`** — carries that selection into a token and component
  contract a developer builds from, as `DESIGN/DESIGN-SYSTEM.md` plus the same
  contract rendered as one page in `DESIGN/DESIGN-SYSTEM.html`.

Both produce **candidate evidence for `Design Ready`, never the approval
itself.** The design-system HTML template is split into a stable semantic
contract and a project-specific presentation layer, which adds no gate,
validator, required artifact, or rule.

See [`docs/concepts/visual-direction.md`](../concepts/visual-direction.md) and
[`docs/concepts/design-system.md`](../concepts/design-system.md).

## Conditional Visual Proof (Milestone 10)

*Optional creative capability, closed by `DEC-022` on 2026-08-11.*

Visual Proof applies **only** when a project has already entered the creative
path — that is, when `DESIGN/VISUAL-DIRECTION.md`, `DESIGN/DESIGN-SYSTEM.md`,
and `DESIGN/DESIGN-SYSTEM.html` all exist. It does not make design systems
universal, does not add a new approval, and makes no automated judgement about
whether a design is any good.

What it checks is evidence **shape and freshness**: that `DESIGN/VISUAL-REVIEW.json`
records a named human's review, that the desktop and mobile captures it names
are committed and hash-match, and that the review is current against its
freshness digest. `VPROOF-001` and `VPROOF-002` carry the findings.

See [`docs/architecture/visual-proof.md`](../architecture/visual-proof.md).

## Fixed: a handoff review could be stale because of the host that read it

*This one reached a user-visible verdict, and is the reason to upgrade.*

Every read feeding a digest used `Get-Content -Raw` with no `-Encoding`.
Windows PowerShell 5.1 decodes a BOM-less file with the machine's ANSI code
page; PowerShell 7 defaults to UTF-8. The same bytes therefore became different
strings, and the SHA-256 over them differed by host:

| Bytes in the file | 5.1 reads | pwsh 7 reads |
|---|---|---|
| `E2 80 94` (UTF-8 `—`) | `â€"` — three chars | `—` — one char |

`HANDOFF-010` then reported a perfectly current `HANDOFF-REVIEW.json` as
**stale**, raising a blocking WARN and exit 2. A team recording a handoff
digest on macOS and validating it in Windows CI hit this in ordinary use, with
no way to make the gate pass. Projects whose governed artifacts are pure ASCII
were never affected, which is what made it hard to see.

Fixed at all five digest-feeding reads, recording side included, so the two
sides cannot disagree: `Get-ReviewInputDigest`, `Get-ProjectText`,
`assess-handoff.ps1`, `handoff-digest.ps1`, and
`Get-VisualProofNormalizedTextHash` — Milestone 10's digest carried the same
latent bug and is fixed in the same change.

**Upgrade note: no action required.** The fix is a no-op on PowerShell 7, which
was already decoding as UTF-8. Digests recorded by 1.4.0 on pwsh 7 remain valid
and no recorded review is invalidated. If you previously worked around a
spurious "stale review" on a Windows PowerShell 5.1 runner by re-recording the
digest there, re-run `scripts/handoff-digest.ps1` once on any host after
upgrading — all hosts now agree.

Recorded as section 7 of
[`docs/architecture/powershell-portability.md`](../architecture/powershell-portability.md).
Closes issue #20.

## Fixed: `dogfood-scope-diff` was red on every `main` run

The job pinned three fixture commit SHAs authored on milestone branches that
were never pushed to `origin`. Once `origin` held only `main` and the release
tags, those commits were unreachable there and every run failed
`SCOPE-DIFF-004` — a case `fetch-depth: 0` cannot fix, because it fetches all
refs but not a commit no ref points at.

The job now builds both delta commits in its own checkout at run time and
asserts each touches exactly the one file its fixture documents. SCOPE-DIFF
still evaluates a real `git diff` over real commits. No validator, rule, or
policy behaviour changed.

## Better failure messages

`-VerifyGolden` now prints the differing lines, with line numbers, when a
golden master mismatches — previously it reported only "output differs from
golden master". That single change is what made the encoding defect above
diagnosable: it reproduced only on a host the maintainer cannot run, and the
job uploads no artifact to recover the real output from.

The diagnostic method behind both fixes, including the wrong turns, is written
up in
[`docs/architecture/lessons-learned.md`](../architecture/lessons-learned.md).
