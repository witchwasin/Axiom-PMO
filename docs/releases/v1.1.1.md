# Axiom-PMO 1.1.1 — Release Notes

A patch release. Two validation rules that were deferred from 1.1.0, and a CI
change that removes duplicated work from the test suite.

No behavioural change to any gate that existed in 1.1.0. A project that passed
`-Gate Handoff` on 1.1.0 still passes, unless it has one of the two defects
below — in which case it had them before and nothing was checking.

## `HANDOFF-013` — table header matches the declared columns

*Closes [#6](https://github.com/witchwasin/Axiom-PMO/issues/6).*

The validator reads table cells **by column name**. Rename `Blocking Point` to
`Blocking`, and `$row.'Blocking Point'` resolves to an empty string — no error,
just nothing there. The gate then reported:

```text
[FAIL] HANDOFF-009 Open action OA-001 has no valid blocking point
```

True of the parsed data, and misleading about the cause. The author looks at the
row, sees `before_demo` written plainly in it, and concludes the validator is
broken. That is worse than a missing check: it spends the reader's trust on a
diagnostic pointing at the wrong thing.

Headers are now asserted against `handoff_document.sections[].columns` and
`build_spec.sections[].columns`, by name and in order. A reordered header is
reported separately from a renamed one, because the fix differs:

```text
Table 'Open Actions' has the declared columns in a different order
  (expected: Action ID | Description | Owner | Blocking Point | Status)

Table 'Open Actions' header does not match the declared columns
  (missing: Blocking Point; unexpected: Blocking)
```

Order is part of the contract by default. Set `table_headers.order_matters` to
`false` if a project genuinely needs the freedom — but consider first whether a
reader moving between two projects benefits from finding the same shape in both.

Reference: [`docs/rules/HANDOFF-013.md`](../rules/HANDOFF-013.md).

## `HANDOFF-014` — handoff artifacts agree with `PROJECT.md`

*Closes [#7](https://github.com/witchwasin/Axiom-PMO/issues/7).*

`Project` was the only field in the handoff metadata block checked against
nothing, while its neighbours were all cross-checked against something the
project declares:

| Field | Checked against |
|---|---|
| `Mode` | the effective mode resolved for the run |
| `Horizon` | ISO-8601 date validity |
| `Build Spec Ref` | a file that exists |
| `Project` | *(nothing, before this rule)* |

The exposure is a project started by copying another — exactly what a filled-in
`HANDOFF.md` invites, since it is the most useful starting point for the next
one. The old project code comes along, everything else passes, and the sheet
names a project that is not the one being validated.

`HANDOFF.md`'s `Project` and `HANDOFF-REVIEW.json`'s `project_code` are both
compared against `PROJECT.md`'s heading. The heading is the authority, not the
directory name: a project can legitimately live in a differently named folder.

**The rule found a real defect on its first run.** `demo/broken-project` and
`demo/fixed-project` had both been copied from `examples/HANDOFF-DEMO` with only
their headings renamed, so their handoff artifacts still said `HANDOFF-DEMO`.
Fixed in the same commit — this repository reproducing the issue's own scenario,
unnoticed until the rule existed.

Reference: [`docs/rules/HANDOFF-014.md`](../rules/HANDOFF-014.md).

## Changed — CI runs the fixture matrix once

Golden verification was a separate workflow step that re-executed all 148
fixture cases, the most expensive thing the suite does, to check output
`run-all-checks` had produced two minutes earlier. The only difference between
the two runs was a flag.

Measured before and after, on the same workflow:

| | Before | After |
|---|---:|---:|
| Wall clock | 7m32s | 6m14s |
| `pmo-checks` (Windows PowerShell 5.1) | 7m29s | 6m08s |
| `pmo-checks-linux-experimental` (pwsh 7) | 6m30s | 4m14s |

Worth noting what the measurement ruled out: Windows was only 13% slower than
Linux, so this was never a platform problem. It was volume, and half the volume
was duplicated — and it grew with every fixture added, 90 to 148 during 1.1.0.

The Windows saving (81s) is smaller than the step it removed (162s), because the
golden comparison itself moved inside the remaining pass rather than
disappearing. What was actually saved is re-running 148 child processes.

No coverage was removed. Verified by reverting a fixture golden and an example
golden in turn, and confirming each still fails the suite with the failing check
named.

## Fixed — the example goldens were verified nowhere

Not in `run-all-checks`, not in the workflow. `tests/golden/capture-examples.ps1
-Verify` is now part of the suite, so the worked examples the README points at
are held to their recorded output. Three cases, negligible cost.

## Compatibility

No migration. `VERSION` and every `pmo-config/*.json` version move to `1.1.1`;
`schema_version` and `diagnostics_schema_version` are unchanged, so nothing
about the machine-readable contracts moved.

A project that adopted the Handoff gate on 1.1.0 needs no edits unless it trips
`HANDOFF-013` or `HANDOFF-014`, both of which report the exact artifact, field,
and expected value.

## Known limitations

Carried forward from [1.1.0](v1.1.0.md), with two now closed.

**Attribution is traceable, not provable.** `reviewer_kind` is a
self-declaration; no offline validator can prove who typed a JSON field. A
closure under a human-only lens must cite a `DEC-###` that exists in
`decision-log.md` with a named decider, which anchors it to a governed artifact
somebody is accountable for. Provable attribution needs signed commits or a
reviewed pull request — both outside this validator.

**No clean-room walkthrough or terminal recording.** *Tracked but deferred —
[#8](https://github.com/witchwasin/Axiom-PMO/issues/8) is closed as **not
planned**, not as done.* Milestone 1 asks for both. `scripts/demo.ps1 -Plain
-NoPause` produces a deterministic transcript to record and `demo/README.md`
gives the `asciinema` command, but no asset is committed and no independent
first-run walkthrough has been performed on any platform.

`clean-room/` ships a container that makes the walkthrough reproducible, in two
modes. That is the tooling, not the work — and the Dockerfile itself has never
been built, because the machine it was written on had no usable container
runtime. Its README says so.

The issue is closed because nobody is scheduled to pick it up, and an open issue
implies otherwise. Reopen it when someone is ready to walk it.

**Cross-platform support is evidence, not a claim.** Windows PowerShell 5.1
remains the reference platform. PowerShell 7 on Linux/macOS is exercised by a
non-blocking CI leg.

**Location fields are partially populated.** `artifact` / `item_id` / `field`
are filled by every `HANDOFF-*` rule and progressively by the older ones. `null`
is a valid state, documented in the
[diagnostics contract](../reference/diagnostics-contract.md).

**Rule pages cover the handoff rules only.** Other rules carry their remediation
in the catalog entry.
